One Player Detail, eight sports

The deep MLB page was approved, and the question it raised was “how do we get an every-other-sport equivalent?” This is that question answered by building it. Every sport below renders the exact same eighteen blocks from the exact same template — switch the tabs and watch the layout hold still while only the content changes. Nothing is hidden for any sport, and there is no sport === 'x' anywhere in the renderer.

What the measurement said

Before designing anything I counted what is actually in player_game_history today — it is JSONB and sport-generic, so one query per sport gives the real ceiling. The premise was wrong. MLB is not the deepest sport in this database; it is mid-table. NFL and CFB carry roughly twice its distinct stat vocabulary.

2,756,058 rows measured 2026-08-29. “Keys” counts distinct stats keys with a non-zero value across a 60k-row sample per sport (40-row sample for the four smaller ones). Golf is absent from this table entirely — it has its own schema, which is a real finding and not a gap.

The reframe that unblocks it

The six blocks that looked MLB-only — pitch mix, strike zone, platoon, park factors, opposing starter, batter-vs-pitcher — are not MLB concepts. They are MLB's instance of six universal roles that every sport fills with its own content: an opponent unit, a usage mix, a spatial grid, a binary split, conditions, and a career head-to-head. Once named as roles, no sport renders a null and no sport needs a branch. Tennis has a serve-placement grid the way MLB has a strike zone.

The same six slots, filled eight ways. This table is the architectural proposal: PlayerDetailData keeps one field per role, and each sport's adapter decides what goes in it.

What this means for the interface

Every page above is the same eighteen blocks in the same order, driven by one renderSport(data) function with no sport check in it. That is not a mockup trick — it is the shape the real component should take, and it lands inside the existing convention rather than fighting it:

  • Six named role fields replace six MLB-named fields. pitchMix becomes usageMix, zoneProfile becomes spatialGrid, platoon becomes binarySplit, opposingStarter becomes opponentUnit. Each carries its own title, axis labels and cells, supplied by the sport's adapter. The component renders a title and a grid; it never knows what a strike zone is.
  • Nothing is nulled for a real sport. The null-renders-nothing rule in CLAUDE.md §4 stays exactly as written — it is just no longer load-bearing for the common case, because a role is fillable by every sport. Golf still nulls the two blocks it genuinely lacks.
  • Tennis is the real constraint, not the tail. Eight stat keys against NFL's fifty-seven. Its page holds up here because the roles pull from match structure — serve placement, surface, opponent profile — not from the game-log JSONB. That is a data-sourcing task, and it is the one place equal depth costs real work rather than real layout.
  • Golf does not use this table at all. It has its own schema and its own genuinely different blocks (liveMatchup, golfFormHoles) that already exist. Its tab shows the roles mapped onto course data; treat it as the one sport where the extension escape hatch is correct rather than lazy.
