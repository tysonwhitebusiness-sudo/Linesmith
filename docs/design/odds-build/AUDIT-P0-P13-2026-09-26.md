## Findings this audit fixed

1. **CI red since 2026-09-06**: three steps named `test_leakage_guard`,
   `test_prop_calibration_applied`, `test_both_sides`, deleted that day with
   the old scoring layer. Steps removed (`d1b9674`).
2. **`test_scraper_volume` (P4's tool)** inserted into `bridge.db`'s
   `game_links` by position; the table gained columns in P6. Now by name.
3. **Pulls read as "the book took the line down" when only a relay had
   dropped its copy.** 24 h: 622k game-line pulls, 415k of them actionnetwork,
   97% back within ~15 min. Scan's "N pulled", the board's pulled rows and
   P12's pulled alert all counted them. An open pull now counts only while no
   source still quotes that book at that line and side; every pull stays
   recorded (D14). `3922de1`.
4. **The sharp price time was a blanket 15 minutes** (P11). Now the exact CDN
   age of the request that carried Pinnacle's prices: median 449 s, p10 92 s
   on 3,000 real snapshots. `bed4b6f` — **live only after the bridge task
   restarts and the worker deploys.**

## Open findings (need the operator or a decision)

0. **During a live game, no sport's game page shows the odds section.**
   Every adapter's live layout leaves out the Lines section on purpose
   ("Lines & props waits for the final", written before this build), so
   P8's odds card and P9's live polling — built for exactly the hours when
   prices move fastest — never render in play. The live stand-in, "Lines now",
   reads the paid feeds' `game_odds_history` (captured ~every 15 min) and
   showed "No prices captured since the first pitch" on MLB 823248 while the
   bridge was writing in-game prices to `game_lines` (D24). Proposed fix: the
   same odds card as the first row of each sport's live "Right now" section
   (one shared helper, no sport branch), replacing "Lines now". A layout
   change, so it waits for the operator's go (mockup first).
1. **The scraper still stalls (P0's 48 h check FAILED).** Four watchdog
   restarts on 09-25 (06:58, 10:28, 11:18, 17:43 UTC), each ~5 min without
   writes. Every dump shows the writer inside SQLite `commit()`, with
   `scraper.db-wal` at **5.3 GB** beside a 22 GB database: the committing
   connection runs the auto-checkpoint, and a WAL that size (held open by long
   reads, P6 fault 1) makes it take minutes. Fix, in odds-scraper: a
   background checkpointer (`wal_autocheckpoint=0` on the writer), a
   `journal_size_limit`, and `PRAGMA wal_checkpoint(TRUNCATE)` at restart. The
   watchdog recovers every time, so data loss is ~5 min per stall.
2. **The worker deploy** (P11 + P12 + the price-time fix). Until then pages
   show no edges (the 5-minute fail-safe) and the health check shows
   `marketEdgeJob: NEVER RUN`.
3. **The bridge task restart** (the price-time fix's laptop half).
4. **Propline's `last_change_at` is still not read** (P7 follow-up, D23).
   Propline rows carry our first-seen time as "since" — conservative for the
   edge, not the source's truth.
5. **Kalshi prop contracts labelled `under` carry the YES price** (P10 found
   it; the bridge should label every N+ contract `over`). Read as stored.
6. **Cost guard is a floor**: $35.38 of $50 projected, with Supabase compute,
   storage, egress and Render bandwidth unmeasured.
7. **P11 gate 6 needs the operator's decision** (below).
8. **Scraper lane (S-G3 … S-G1): not started** — every item was to wait for
   its own green light; `TIERS` is unchanged.
9. P13 cannot be read before deploy + 3–5 days.

## Phase by phase

### P0 · Keep the data flowing (laptop)
- **Plan:** the scraper never stops silently; its history has an off-machine copy.
- **Built:** freshness watchdog + stall dump (odds-scraper `52ae6b4`, `8afa4d8`), raw pruning moved off the writer thread (`8d0fb08`), daily `OddsScraperBackup` with verify.
- **Now:** backup verified 09-24 (17.4M rows, 0 mismatches). **Stalls continue (open finding 1)** — a different cause from the pruning one P0 fixed; the watchdog restarts each within ~6 min.
- **Deviations and why:**
  1. `run-scraper.ps1` rewritten to start the scraper detached — the spec missed that the old script blocked, so the task's 5-minute trigger never ran.
  2. The stall drill switch is a file as well as an env var — an env var cannot be set on a running process.
  3. Backups upload in 40 MB chunks — Supabase refuses objects over 50 MB.
  4. py-spy skipped (a download).

### P1 · Fix what is broken (TypeScript + Python, deployed `4d64071`)
- **Plan:** four page bugs and game-line history losing line moves.
- **Now:** the history logs a point move at an unchanged price (`test_game_odds_history_point` passes live; 1.2M game-line history rows/24 h).
- **Deviations and why:**
  1. Game-line `source` is the line's own writer, not the table name the spec gave — the frozen Scan chip reads `source` as provenance.
  2. Home/away labelled from `playerSide` — the spec's labels were wrong for every away player (and already wrong on MLB).
  3. "Betr (AU)" naming — the spec's table named two books "Betr".
  4. Found and fixed a `yield_fn()` bug (`e8b5a89`) that killed `tennisStatsJob`.

### P2 · Names (labels + book registry)
- **Plan:** every scraper price nameable: market, book, whether it is a price.
- **Now:** coverage 99.9% of prop rows, 96.5% of game markets (gates met); drift tests pass.
- **Deviations and why:** a `SKIP` set added beside `VERIFY` (NASCAR "finishing position", yes/no specials, season futures — no app market); 6 low-volume labels left unmapped (under 30 rows/day, no app market); registry +3 books.

### P3 · Matching (laptop)
- **Plan:** link scraper games and players to app ids with no wrong links.
- **Now:** zero wrong links in the 170-game / 215-player hand check; today MLB 99.9%, NFL 99.6%, CFB 89.2%, MLS 96.1%, NHL 100% of prop rows linked.
- **Deviations and why:** an MLB roster fallback (StatsAPI, with positions) — the snapshot roster had no positions and linked only 88.7%; tennis name matching ported (the scraper's rule read "Sinner J." wrong); a "Man"→"Manchester" alias; team matching moved into `entity_resolution` so the harvester shares it. NHL rosters were routed to P6 and are done there.

### P4 · Storage decision ⚑
- **Plan:** measure options A–F (each storing less), the operator picks one.
- **Changed completely:** the operator rejected every option that dropped data (D14) and decided **D24** — everything reaches Supabase, compact, 10 days hot, then the corpus; the disk grown to 27 GB and held by our own guard at 85% — plus **D25**, a $50/month ceiling. The measurement stands; the options table is superseded.
- **Deviation:** measured one full day, not two — only 09-24 had all 29 sources.

### P5 · Schema and writers (deployed `c5b9cf7`)
- **Plan:** two times per price, pulls, openers, periods, splits, exchange books; first-hand over relayed.
- **Now:** 1.44M prop + 1.24M game-line history rows/24 h, 100 day partitions, exports verified (16 prop + 15 game-line days, 5 each dropped), disk 5.8 of 22.95 GB, window 10 days.
- **Deviations and why:**
  1. **A1 compact history** (from D24): `prop_odds_history` converted row for row into the coded, day-partitioned `prop_price_history` (341 → 101 B/row) and dropped, with one reader per language — the spec's text layout would not fit D24's volume.
  2. **A2 disk guard + history mover** — added by D24; the mover runs in the cron because the worker peaks at 477 of 512 MB.
  3. `price` is `integer` (41,451 values exceed `smallint`); `decimal_odds` and `id` kept.
  4. A covering index tried and reverted on measurement; the legacy proof writes supplements rather than re-exports (re-exporting would lose pruned rows).

### P5.1 · Hardening (added by the operator)
- **Plan:** did not exist; moved out of P5's "found, not fixed".
- **Built:** RLS on **20** tables (P5 had counted 3; anon could write to all); the corpus export gap fixed at its cause, 14,415 rows backfilled.
- **Now:** no public table without RLS (queried).

### P6 · The bridge (laptop; health check deployed)
- **Plan:** every matched change reaches the app within ~1 min, with its own times, under D24, with a heartbeat.
- **Now:** lag 27–37 s; 3.5M offers read and 1.85M changes confirmed since its 15:45 start; heartbeat healthy.
- **Deviations and why:**
  1. The spec's amendments (it predates D24).
  2. **Unmatched prices kept with their prices** (spec correction 2).
  3. Standing prices **backfilled once per newly linked game** — a spec gap: changes-only forwarding never delivered a price unchanged since before the link (Pinnacle's MLB run line).
  4. Four live faults fixed (an SQLite snapshot pinned by an implicit transaction, a lock held across roster fetches, a full-table start-up scan, a slow cold lookup) plus laptop write latency fixed at the shared writers.
  5. Connections measured by TCP (the pooler hides `application_name`).
  6. P7's daily run lives inside the bridge's cycle, not its own task.

### P7 · Timing
- **Plan:** measure how late each source is; decide which may be the sharp reference.
- **Now:** `source_latency` 423 rows, last run 09-25 10:33 (daily).
- **Deviations and why:** game lines only (Pinnacle quotes almost no props in the scraper); T0.4 added (spec correction 5). **Result that shaped P11:** no relay is proven fast, and Circa via VSiN is not. Open: Propline `last_change_at` (open finding 4).

### P8 · The odds sections
- **Plan:** the approved mockup's odds surfaces on player, game, team pages and the Slate.
- **Now:** every route 200. Rendered in this audit (1440 + 400, no overflow, no page errors): the player page (CFB 4921110 — Best price, Every book, Where the money is, Line movement, the Edge card), the team page ("Against the closing number"), the Slate (Games, Movers, Market), `/kit`. **The game page in play shows none of it (open finding 0).**
- **Deviations and why:**

  2. `GamePropsCard`/`PropsResults` not built — each sport's props card already reads the same data and grades finals.
  3. The old final "Game lines" card kept — it holds the only close for games older than the 10-day window (D14).
  4. Scan's card view did not get the D22 cells (the table did).
  5. Its Result said `EdgeCard` and `MoneyCard` were "on /kit" — they did not exist; P10 and P11 built them.
  6. Plus spec corrections 3 and 4 (chart pulls/consensus; the Dropping odds list).

### P9 · Live
- **Plan:** 30 s polls, diffs, motion.
- **Deviations and why:** polls every **45 s**, not 30 — the spec's own load bar failed at 30 s (p95 1.08 s at 45 s from the laptop); the game page polls a light payload and merges it; every `/api/odds/*` read moved out of the 10/min provider rate limit (pages froze on 429s); a line move reads as a change, not a pull (a rule the spec did not state).

### P10 · Where the money is
- **Deviations and why:** splits ride on the existing game/player payloads (so they refresh with P9's poll) instead of a new route; no footer naming banned words (the guard bans the words themselves); Kalshi `under` rows read as stored (open finding 5).

### P11 · Edge (built; deploy pending)
- **Plan:** a sharp-vs-soft market edge behind 11 gates, logged, with a kill switch and a self-check.
- **Now:** kill switch drilled (hidden 22 s after the flip, back in 19 s); auto-off drilled (tripped, alerted, hid, cleared after 3 runs); routes serve `edges` only while visible and fresh.
- **Deviations and why:**
  1. **Gate 6 uses the minimum of multiplicative, power and Shin; worst case is logged, not gating.** Worst case turned both edges the spec required to reproduce negative (GB +1.0% → −1.4%, London +1.8% → −3.2%). **Needs the operator's decision.**
  2. London shows +1.6% (the minimum, power) where the mockup said +1.8% (multiplicative).
  3. **The sharp price time** was first the 15-minute bound; fixed today to the exact copy age (finding 4).
  4. The Slate reads `/api/odds/edges` (uncached) — its 60 s cache would outlive the 30 s kill switch.
  5. The auto-off drill injected fake prices in memory, never into live tables.
  6. A 5-minute fail-safe added: no edge older than that is shown.
  7. `market_edges` keys with `UNIQUE NULLS NOT DISTINCT` (a moneyline's line is NULL).
  8. The Edges tab lives in `SlateOddsHub`/`SlateEdges`, not `SlateMarket.tsx`.
  9. Runtime from the laptop 19–65 s; the worker's p95 must be read on NFL Sunday after the deploy (> 20 s → move to the bridge cycle).

### P12 · Alerts, slip, flags (built; flags deploy pending)

- **Deviations and why:** steam for alerts and flags is 30 min (the spec) over P8's 45-min steam; a steam run needs 3 independent observations (one relay snapshot moved 5 books "in 0 minutes"); the money split is |money − bets| ≥ 15 (P10's rule); a header bell built (none existed); the slip uses the Best price card's rule (it first picked a D19 outlier); two missing tennis read templates fixed in passing.
- **Not seen:** alerts on a signed-in page (no test account).
