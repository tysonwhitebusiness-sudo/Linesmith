# Premium/Paid-Tier Feature Gating Audit — 2026-08-18

Monetization and technical-feasibility audit of the current codebase. No new features are proposed. Every claim below is traceable to a specific file inspected directly (page/route/component/lib module); anything not directly verified is marked **unverified**.

**Headline fact, confirmed first because it governs everything else:** there is no auth or identity system anywhere in this app. `package.json` has no auth library (no NextAuth/Clerk/Supabase-auth/etc. — only `next`, `react`, `better-sqlite3`, `@anthropic-ai/sdk`, `xlsx`). There is no `middleware.ts` anywhere in the repo. `lib/db/schema.ts` has no `userId`/`deviceId`/`accountId` column on `picks`, `bets`, `watchlist`, or `pick_history` — every route scopes only by `sport`, not by who's asking. A repo-wide grep for `tier|entitlement|premium|isPro|subscription|paywall|auth\(` turns up zero real hits — the only "tier" matches are `tier1Providers`/`tier2Providers` in [lib/odds/props/registry.ts](../lib/odds/props/registry.ts) (odds-*provider* priority, not user tiers) and a statistical `trustTier`/rank-bucket concept in [components/PlayerDetail.tsx](../components/PlayerDetail.tsx) and [components/GameDetail.tsx:1285](../components/GameDetail.tsx). **This means every single feature below starts from the same baseline: zero existing gating, and no server-side concept of "which user is this" to gate on.** That baseline is stated once here rather than repeated in every table row.

## Step 3: Unsafe or Impractical to Gate

- **MLB scoreboard/slate and NFL player detail are structurally ungateable as scoped features.** The MLB slate route ships the entire day's data (~19MB per the route's own comment) to every client in one call, and every other MLB page/component is just a client-side `.filter()` over that array. NFL player detail goes further: there is no server round-trip at all for that page — the data is already resident in the browser via the `/api/nfl` snapshot before the player page even mounts. Gating either of these "features" really means gating the parent sport's entire snapshot response, not the feature itself.
- **Prop Score / edge model is not a server feature at all.** `computePropScore` ([lib/odds/props/propScore.ts:113](../lib/odds/props/propScore.ts)) executes in the browser bundle, over `subjectMeta` fields and `propRows` that are already shipped for other reasons. A UI paywall (blur the badge, hide the component) does nothing — the unminified function and its inputs are sitting in the page's JS and network responses regardless. This is the single weakest candidate for "hide it and call it gated" in the whole app.
- **Golf prediction models (the actual proprietary IP) are the least protected of anything audited.** The Monte Carlo tournament-win model and hole/round models are commingled into the public `/api/golf` snapshot (`modelProb`, `tournamentPrediction` fields, unconditionally present on every candidate) *and* separately exposed through a standalone `app/api/golf/predictions/route.ts` that is explicitly labeled a "testing" endpoint with no auth of any kind — it's callable directly with `curl`. If any feature here is worth charging for, this is it, and it's currently the most exposed.
- **Field-wide golf advanced stats are leaky by deliberate design, not oversight.** `app/api/golf/field-stats/route.ts`'s own comment explains it returns the whole field in one call specifically to avoid 69 separate per-golfer requests — a reasonable engineering tradeoff that happens to also mean there's no per-golfer boundary to gate against.
- **Bets/Picks/Watchlist have no identity concept to gate on.** `lib/db/schema.ts` confirms none of these tables have a `userId`/`deviceId` column. Gating any of them today would gate the single implicit user of the whole self-hosted app — there's no "my bets vs. someone else's bets" concept yet, so premium-gating here is really "does this whole app instance get to use bet tracking," not a per-account decision.
- **`app/api/odds/lines/route.ts` mixes a free-tier-appropriate feature (raw odds comparison) with paid-provider-adjacent side effects (MLB pick-locking) in one 455-line handler.** Gating "just the odds comparison" cleanly would require pulling the pick-lock logic out first; gating the whole route would also gate a model-locking cycle other code depends on.
- **Data trivially available elsewhere:** the raw game-odds comparison feature (the-odds-api.com passthrough) and golf tournament betting lines (SharpAPI passthrough) are both unmodified third-party sportsbook prices — a user can see the same numbers on the sportsbook's own site or a free odds-comparison site for free. Charging for the *display* of these specific numbers (as opposed to the *analysis* built on top of them) is a weak value proposition on its own.

## Step 4: Ranking

**High feasibility + high differentiation (best candidates)**
- **"More Books" (Tier 2)** — [app/api/props/more-books/route.ts](../app/api/props/more-books/route.ts): already has the exact enforcement shape a tier gate needs (budget + cooldown check), is a single contained route, and unlocks something the free tier genuinely doesn't have access to (an additional, metered odds source).
- **"Check Sharp Price" / Line history (Tier 2)** — same reasoning; both are single-route, already budget-gated, and pull from the tightest-capped provider (250/mo) in the stack, making them a natural "premium unlocks the scarce thing" story.
- **MLB team statcast/batter ranks, bullpen strength, home run candidates, injuries, recent/H2H, NFL team detail/grades, golfer player detail** — all single, self-contained per-request routes with real caching already in place; a tier check drops in cleanly with S effort each, and each is a genuinely deeper stats layer beyond the free scoreboard.

**High feasibility + low differentiation (gate if needed, low upside)**
- **Game odds comparison (`game-lines/route.ts`)** and **golf tournament betting lines** — easy to gate (contained, cacheable, S effort) but the underlying data is an unmodified third-party price feed available elsewhere for free; gating the raw number has weak willingness-to-pay even though it's technically trivial.
- **Golf schedule, standings, MLB teams index** — easy S-effort gates on genuinely public, low-value data.

**Low feasibility + high differentiation (valuable but needs refactor first)**
- **Golf prediction models** — the most differentiated IP in the app (a real Monte Carlo simulation, not a passthrough), but it's currently embedded unconditionally in a public snapshot and duplicated in an unauthenticated test endpoint. Refactor needed: split model output out of the general snapshot response into a separately-gated field or endpoint, and either lock down or remove `app/api/golf/predictions/route.ts` from being publicly reachable.
- **Prop Score / edge model** — differentiated (a real scoring heuristic over live odds + model probability), but computed entirely client-side today. Refactor needed: move `computePropScore` server-side, and stop shipping its raw ingredients (`subjectMeta.modelProb/leagueRate/modelSampleSize`, full `propRows`) to ungated clients.
- **MLB scoreboard/slate and NFL player detail** — both sit behind the most-used pages in the app, but neither has a scoped enforcement point today; the whole sport's data ships in one blob. Refactor needed: either split the snapshot into a free/premium-field split at serialization time, or accept that gating here means gating the entire sport's data, not a sub-feature of it.
- **Bets/Picks/Watchlist** — potentially a nice "save your picks" premium hook, but there's no per-user identity in the schema at all yet. Refactor needed: add an identity column before any of this can be gated per-account rather than per-instance.

**Low feasibility + low differentiation (not worth gating)**
- **Batter-vs-pitcher/pitching matchup cards, tournament detail cards, player-vs-defense card, standings** — all pure client-side derivations of data already fetched for other purposes, with no independent fetch of their own to gate, and none carry data a user would pay specifically for.

## Refactor Prerequisites

None of the gating work above can be enforced server-side today without first building:

1. **Any identity/auth system at all.** There is currently no way to know "which user is making this request" anywhere in the stack — no session, no login, no `userId` column on any table. This is the single hard blocker; every other item below is meaningless without it.
2. **A `user.tier` (or equivalent entitlement) field and a place to check it.** There's no middleware layer in this app — "all routes call the DB/adapters directly from route handlers" — so the check has to be added per-route (as shown in Step 2's "What Needs to Be Built" column) or centralized in a small number of shared functions (`lib/cachedRoute.ts`, `lib/db/client.ts`'s `readPropOddsForGame`) that many routes already funnel through.
3. **An identity column on `bets`, `picks`, and `watchlist`** ([lib/db/schema.ts](../lib/db/schema.ts)) — without it, gating those features is an all-or-nothing switch for the whole app instance, not a per-account decision.
4. **Response-shaping / field-level filtering, not just route guards, for the two highest-differentiation candidates.** Golf's prediction fields and the props Prop-Score ingredients are currently baked unconditionally into otherwise-public payloads (the golf snapshot, the props odds feed, the client bundle). A route-level "are you allowed to call this endpoint" check would not fix either of these — the free-tier response itself needs to omit the fields, which is real serialization work, not configuration.
5. **A decision on `app/api/golf/predictions/route.ts`'s production exposure** — it's currently a fully open, unauthenticated endpoint documented in its own code as a testing/integration route, directly exposing the same model output discussed as the top differentiation candidate above.
